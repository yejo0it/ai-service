- 측정일: 2026-10-27 (8단계, 축소안)

## 1. 요약

- 입력 토큰: 대표 13개 시나리오 평균 **11,865 → 7,580 (−36.1%)**. 결정적인 값이다(count_tokens).
- 요청당 비용: 실제 호출 6개 시나리오 평균 **$0.0317 → $0.0163 (−48.6%)**. 각 1회 측정이며 현재 버전 6회 중 2회는 캐시 쓰기 호출이다.
- 출력·thinking 토큰과 응답 시간: 평균 −6~−10%였지만 시나리오별로 +35%~−52%를 오가 **최적화 효과로 단정할 수 없다**(1회 측정).
- 정확성: 측정 범위에서 **최적화로 인한 회귀 증거는 없다**. 다만 다음 문제는 최적화와 별개로 남아 있다.
  - '넷째 날'을 `day_index=4`로 해석하는 오류: 현재 4회 중 3회, 이전 3회 중 2회 (최적화 전부터 있던 문제)
  - 복합 요청(C4)에서 답변 문장의 날짜가 실제 일정과 다름
  - 전체 재구성의 변경 효과가 낮음: 현재 3회 이동 0·0·1건, 이전 1회 0건 (Issue #90)

## 3. 측정 조건

- 가짜 여행: 도쿄 5박 6일(2026-11-10~15), 일정 25곳(하루 2~5곳), 숙소 신주쿠 워싱턴 호텔(11-10~13). DB 트랜잭션 안에서 만들고 측정 후 롤백했다.
- 이전 버전: `git show c2226fd:backend/trips/ai_planner.py`를 별도 모듈로 불러 같은 여행에 썼다(압축 전 컨텍스트, 원래 스키마·프롬프트, 캐시 없음, **항상 RAG 검색**).
- 현재 버전: `trips.ai_planner.propose` 그대로. RAG는 서버와 같은 규칙(`rag_policy.guide_search_decision`)으로 판단했다.
- A·B 묶음은 `propose`를 직접 호출했다(뷰의 장소 확정·이동 시간 계산은 제외). C 묶음만 실제 뷰(`/ai/propose/` → `/ai/apply/`)를 거쳤고 Google Places는 가짜 결과로 모킹, Routes·NAVITIME은 끈 상태(직선거리 배치)다.
- RAG 문서: 실제 수집된 여행 정보 코퍼스(청크 1,197개). 측정 전 한 번 검색해 임베딩 모델 로딩 시간을 뺐다.
- 호출 순서: A는 시나리오마다 이전 → 현재를 번갈아 호출했다. 캐시는 5분 동안 유지되므로 순서에 따라 캐시 쓰기/읽기가 달라진다(표에 표시).

### 비용·시간 계산 기준

- 단가(Sonnet 5, 1M 토큰당): 입력 $2, 캐시 쓰기(5분) $2.5, 캐시 읽기 $0.2, 출력 $10. thinking 토큰은 출력에 포함된다.
- 비용 = `input_tokens × 2 + cache_creation × 2.5 + cache_read × 0.2 + output_tokens × 10` (÷ 1,000,000). **응답의 usage로 계산한 값이며 실제 청구 금액과 대조하지 않았다.**
- '캐시 적중 가정' 비용: 캐시 쓰기 호출의 6,307토큰을 캐시 읽기 단가로 바꿔 계산한 추정값이다.
- 처리 시간 = RAG 검색 시간 + Claude API 시간(A·B). C 묶음은 뷰 전체 시간(`ai_request.total_ms`)이다.

### 측정값의 한계

- **각 1회 측정**이다. 출력·thinking·시간은 같은 요청에서도 크게 달라진다(예: 현재 버전 재구성 3회의 출력 1,953~4,968, 시간 23~55초). 시나리오별 변화가 +35%~−52%로 엇갈려 출력·시간 감소를 최적화 효과로 단정할 수 없다. 확실한 효과는 입력 토큰·캐시·RAG 생략이다.
- 현재 버전 6회 중 2회(1 장소 추가, 8 재구성)는 캐시 쓰기 호출이라 비용이 높게 잡혔다. 캐시 적중을 가정하면 각각 약 $0.0095, $0.0239이고 평균 절감률은 약 −64%가 된다(추정).
- 처리 시간은 RAG 검색 + API 시간이다. 이전 버전으로는 뷰 전체(장소 확정·이동 시간 계산)를 실행할 수 없어 뷰 기준 전후 비교는 하지 않았다.
- **나머지 7개 시나리오(4·5·7·9·10·11·13)는 실제 호출로 전후 비교를 하지 않았다.** 이 시나리오의 비용·출력·시간 효과는 4장의 입력 토큰과 이전 단계 측정으로만 판단한다.

### 캐시 적중률(이번 측정)

현재 버전 호출 18회(A 6, B 8, C 4) 중 캐시 읽기 16회, 쓰기 2회로 **89%**다. 연속 측정이라 높게 나온 값이며 운영 적중률(사용자별 요청 간격에 좌우)은 운영 로그가 없어 알 수 없다. 운영에서는 `claude_call`의 `cache_read_input_tokens`로 확인할 수 있다.

## 7. 발견된 문제

### 7-1. '넷째 날'을 `day_index=4`로 해석 (최적화 전부터 존재)

- 요청: "둘째 날 시부야 스카이를 넷째 날 저녁 7시로 옮겨줘" (기대: `day_index=3`, 11/13 19:00)
- 결과: 현재 버전 4회 중 3회(B 2회 + C3), 이전 버전 3회 중 2회가 `day_index=4`(11/14)로 옮겼다. 답변에도 "넷째 날(11/14)"이라고 적는다.
- 형식 검증(id·기간)은 통과하므로 사용자가 미리보기의 날짜를 확인하지 않으면 원하지 않은 날짜로 저장된다.
- 이전 버전에서도 같은 비율로 발생해 **최적화로 생긴 회귀가 아니다**. 참고로 현재 컨텍스트는 일정 줄을 `3 2026-11-13: …`처럼 번호만 쓰고(2단계), 이전은 `- day_index 3 (2026-11-13): …`였다. 표기 차이가 원인인지는 확인하지 않았다(이전 형식에서도 발생).
- 오류가 난 현재 버전 호출의 thinking은 36·58·64토큰으로, 정상 호출(170)보다 짧았다(관찰, 인과 미확인). 이전 버전은 오류 호출도 156·168토큰이었다.
- 후속: 날짜 해석 정책(서수 → day_index 변환을 서버나 프롬프트에서 명확히) 별도 이슈.

### 7-2. 복합 요청(C4)의 답변 문장 불일치

- 요청: "둘째 날 블루보틀은 빼고, 넷째 날 점심에 라멘집 하나 넣고, 다케시타 거리는 셋째 날로 옮겨줘"
- 답변: "**넷째 날** 일정에서 블루보틀 아오야마는 빼고, 다케시타 거리는 셋째 날 **아사쿠사 근처** 동선에 맞춰 옮겨드릴게요" — 블루보틀은 둘째 날 일정이고 셋째 날은 아사쿠사 일정이 아니다.
- 미리보기·적용 흐름은 정상이었지만, C 측정은 변경 내용(뺄 id·이동·추가 날짜)을 기록하지 않아 **답변 문장만 틀렸는지 변경 자체도 틀렸는지는 확인하지 못했다**. 같은 요청이 A에서는 이전·현재 모두 통과했다.
- 후속: 답변 문장과 실제 변경 내용의 일치 검증(예: 답변의 날짜 표현을 서버가 변경 내용에서 만드는 방식) 검토.

### 7-3. 전체 재구성의 낮은 변경 효과 (Issue #90)

- "전체 여행 경로를 동선 위주로 다시 짜줘": 현재 3회 이동 0·0·1건, 이전 1회 0건. 모델은 "이미 지역별로 잘 묶여 있어 재배치할 필요가 없다"고 답했다(가짜 여행이 실제로 지역별로 묶여 있음).
- 그런데 비용은 가장 크다: 현재 3회 출력 1,953~4,968토큰(thinking 1,636~4,640), 23~55초, 회당 $0.038~0.054.
- 같은 요청에 이동 0~14건이 나오던 기존 편차 문제와 같다. 재구성 지침·일관성 개선 이슈 **#90**에서 품질과 함께 비용(불필요하게 긴 추론)을 다룬다.

## 8. 최종 판단

- 비용에 가장 큰 효과: 3·4단계(고정 입력 6,307토큰을 캐시 단가로 처리)와 7단계(수정 요청의 RAG 생략).
- 가장 큰 남은 비용: 전체 재구성(출력·thinking이 길고 결과는 적음) → #90.
- 정확성 회귀: 측정 범위에서 없음. 날짜 서수 해석과 답변 문장 일치는 최적화와 별개로 개선 필요.
- 추가 측정이 필요하면: 운영 로그(`claude_call`·`ai_request`)를 모아 실제 캐시 적중률·요청 유형 분포·RAG 생략률을 확인하는 것이 시나리오 측정보다 정확하다.

## 10. 재현 방법

측정 스크립트는 저장소에 포함하지 않았다(11장). 다시 측정하려면 같은 조건으로 다음을 준비한다.

1. `.env`에 `ANTHROPIC_API_KEY`가 있고 여행 정보 코퍼스가 수집된 상태(`python manage.py ingest_guides`)에서 `docker compose up -d`.
2. 이전 버전 플래너를 컨테이너에 둔다: `git show c2226fd:backend/trips/ai_planner.py > old_ai_planner.py` 후 `docker cp old_ai_planner.py pinroute-backend:/tmp/`. 불러올 때 `from .chat_guard`를 `from trips.chat_guard`로 바꿔 별도 모듈로 실행한다.
3. 3장의 가짜 여행을 트랜잭션 안에서 만들고 `days_map(trip)`으로 일정을 만든다.
4. 각 시나리오를 이전(`old.propose(trip, days, items_by_day, conversation, None, refs)`, refs는 항상 `search.search_for_trip`)과 현재(`ai_planner.propose(..., source=ai_usage.SOURCE_EVALUATION)`, refs는 `rag_policy` 판단대로)로 호출한다.
   - 입력 토큰: `anthropic.Anthropic`을 모킹해 `messages.parse`로 갈 인자를 받은 뒤 `max_tokens`를 빼고 `messages.count_tokens`에 그대로 넘긴다(무료).
   - 실제 호출: 실제 클라이언트를 감싸 응답의 `usage`(input·cache_creation·cache_read·output·`output_tokens_details.thinking_tokens`)와 시간을 기록한다.
5. `docker compose exec -T backend python manage.py shell < 스크립트`로 실행하고, 끝나면 트랜잭션을 롤백한다.
6. 정확성 판정 기준(사람이 정한 기대값): 1 = '도쿄 타워'를 day_index 2에 추가·삭제 없음 / 2 = 나카미세 거리만 삭제 / 3 = 센소지 day_index 0, 10:00 / 6 = 블루보틀 삭제·다케시타 거리 day_index 2·라멘집 day_index 3 / 8 = 이동 1건 이상·삭제 없음(이동 0건이면 '편차: 변경 없음') / 14 = 일정 변경 없음 / 넷째 날 = 시부야 스카이 day_index 3, 19:00 / 기간 밖 = 일정 변경 없음. 모든 시나리오 공통으로 실제 id·기간 안 날짜·한국어 답변.
