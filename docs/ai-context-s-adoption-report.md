# Issue #90 S 최종 채택 및 서비스 적용 보고서

## 1. 작업 요약

최종 채택안은 S(단순 최적화)다. `feature/90-ai-route-reorganization`에서 평가에 사용한 압축 공통 지침·재구성 상세 지침과 위치 컨텍스트를 모든 요청에 전달하도록 적용했다. S 적용 및 파일 정리 과정에서 새로운 모델 API 호출은 하지 않았다.

## 2. 주요 변경 사항

- 수정: B의 요청별 분기 대신 두 고정 시스템 블록을 항상 전달한다. 각 블록의 기존 ephemeral 캐시 설정과 평가 당시 문구를 유지한다.
- 유지: 중복 지침 통합, 날짜 대응 정보와 일정 ID의 중복 제거, 일정별 종류·좌표·체류 시간의 인라인 표기, 숙소 좌표를 유지한다. 장소 보존·고정 일정 유지·최소 변경·명시적 요청 우선 및 AI 제안/서버 검증·적용 역할을 유지한다.
- 삭제: `planner_policy.py`, `test_planner_policy.py`, 정책 선택 호출, 위치 생략 옵션, 요청별 시스템 블록 선택 함수와 선택 인수를 제거했다. 이 두 파일은 앞선 B 작업에서 추가한 미커밋 파일이었다.
- 추가: 실제 S 평가 입력을 고정한 스냅샷과 서비스 입력 동등성 테스트를 추가했다.

일반 질문에서도 압축된 위치·재구성 지침을 보낸다. B의 일반 질문 입력 절감 일부를 포기하는 대신 모호한 후속·복합 요청의 분류 유지보수 부담을 없앤다. 기존 RAG 검색 분류는 별도 기능이므로 유지한다.

## 3. 구현 상세

`propose`는 최신 여행·일정과 미적용 초안을 `trip_context`로 구성하고 마지막 사용자 메시지 앞에 붙인다. RAG 자료는 기존처럼 검색된 경우에만 메시지에 추가한다. `_parse`는 항상 같은 두 시스템 블록과 기존 모델·출력 스키마를 사용한다. API 응답 형식, DB 모델, 프런트엔드 상태 관리와 미리보기·적용 코드는 변경하지 않았다.

날짜 행에는 `day_index=0 (1일차, YYYY-MM-DD)`처럼 인덱스·실제 일차·날짜를 함께 표시한다. 각 일정의 `#ID`, 이름, 등록 시간·시간 표기, 종류, 좌표, 체류 시간을 연결한다. 좌표는 평가와 동일한 소수점 세 자리이며 여러 정류장 좌표는 중복 제거 후 순서를 유지한다. 유효 좌표가 없으면 `미상`으로 표시하고 추정하지 않는다. 숙소는 ID·이름·체크인/체크아웃·좌표를 유지한다.

평가 실행 당시 보존한 요청 manifest와 실제 40회 결과의 해시를 대조한 뒤, 서비스 변경 전에 독립 스냅샷을 저장했다. 혼합·이미 묶인 일정·좌표 누락·근처 장소·후속·복합·준비물·환전의 8개 사례를 실제 서비스 `propose`로 생성해 시스템 블록, 메시지, 요청 SHA-256, 모델, 최대 출력 토큰, 응답 스키마를 비교한다. 재구성·후속·복합 사례는 S와 완전히 같았던 B의 실제 호출을 근거로 사용하며 독립 S 표본으로 세지 않는다.

## 6. 후속 작업

다음 두 항목은 이번 최적화와 분리한 미해결 개선 과제다. 이번에는 코드를 추가하지 않았다.

## 7. 보존한 평가 결과와 한계

A는 Issue #90 추가 최적화 전, B는 조건부 최적화, S는 압축된 전체 지침·위치를 항상 보내는 구성이다. 동일한 도쿄 3박 4일 가상 여행·질문·고정 대화 이력·claude-sonnet-5·max_tokens=16000·응답 스키마로 비교했다. RAG·Places·Routes·사용자 DB는 제외했다.

최종 비교는 최초 8회와 추가 32회를 합한 40회(A 18, B 18, S 4)다. 중간 8회·1회·32회 기록의 응답·usage·요청 해시·비용·시간이 통합 원본에 포함됨을 확인하고 중복 파일을 삭제했다. 자연어 날짜 오류로 1회에서 중단한 뒤 기준을 조정해 재개했으며, 구조화된 데이터 무결성 오류와 API·예산 문제를 중단 기준으로 유지했다.

S 채택 이유는 재구성 입력과 보호 정책을 유지하면서 7종 정규식 기반 분류의 유지보수 부담을 없애는 것이다. B의 추가 비용 이득을 입증하지 못했지만 모든 요청에서 S가 우월하다는 의미는 아니다.

### 유형별 토큰·비용·캐시 기록


다음은 추가 32회 묶음의 같은 사례끼리 비교한 값이다.

### 초기 Issue #90 구현과 입력 증가 배경

아래는 추가 A/B/S 최적화 이전 별도 단계 평가다. 최종 40회 비용에 포함하지 않는다.

grouped와 missing은 매번 변경 없이 유지했다. 각 시나리오의 세 응답에서 구조화된 변경안은 한 종류로 같았다.
